# Frontend structure: how the interface of a data-heavy business app is organized

Objective served: a guide that supports Bernardo and the agents building the app when they decide how screens, state, forms, data fetching, boards and charts are structured. Mode: broad. What a state change triggers belongs to Business logic, which indicators exist to Metrics and reporting, and performance and accessibility to Frontend experience.

Findings are marked **Source finding** (what a cited source says), **Synthesis** (a pattern across sources) or **Inference**. Citations give the document, its section and, where the collection recorded them, the lines of the collected copy; the Source key at the end gives the links.
## 1. The answer

The evidence is framework and library documentation, product documentation (Jira, Shopify, Stripe, Grafana, Metabase, Tableau, Rossum, Supabase) and individual issue and review reports. It describes structures and their stated limits; it does not compare them, so the guide gives decisions, trade-offs and a reversibility view, not a prescribed architecture.

### 1.1 Decisions to settle first

The ordering below is a **synthesis for the brief**, not a recommendation made by any single source. It narrows decisions from stable boundaries toward interaction-specific structures.

1. **Keep view state, server data, and editable drafts distinguishable.** Let a view own transient controls and derived display values; give remote records a cache/fetch boundary; lift state only when multiple views must coordinate. This makes refresh and draft-preservation decisions visible. Sources: React “Managing State” (local/derived/shared state); TanStack Query “Important Defaults” and “Query Invalidation” (remote cache); React Hook Form FAQ (async defaults and dirty values).
2. **Choose list processing and filter scope together.** Client processing suits data already available to the view; server processing fits result sets where filtering, sorting, pagination, facets, and totals must describe the full dataset. Keep those operations on one side of the boundary. Use URL state when filters/sort/page should be addressable or shareable; treat it as view identity, not a substitute for server authorization. Sources: TanStack Table “Client-Side vs Server-Side” and “Column Filtering”; Next.js “page.js” and “Form Component.”
3. **Represent a board drop according to its meaning.** Separate rank changes from status transitions. For transitions with required fields or rejection conditions, use a transition step and a server acceptance/failure boundary; show drag preview as temporary state and reconcile or restore after the response. Sources: Atlassian “Monitor work in a kanban space” and “Transition a work item”; dnd-kit “Managing Sortable State”; React “useOptimistic.”
4. **For machine-assisted forms, preserve provenance and make confirmation an explicit human action.** Evidence supports paired source-and-fields review, visible machine/human status, correction paths, and confidence-based routing. A distinct end-user confirmation structure for extraction-prefilled long forms is not directly evaluated in the collection, so the exact interaction remains a design choice rather than an established pattern. Sources: Rossum “Getting Started” and “Guide to Automation Process”; AWS Textract “Best practices”; LAFF paper.
5. **For dashboards, define each filter’s scope and each chart’s data/render boundary.** A shared control only affects panels/cards explicitly wired to it; local or cascading controls may be narrower. Treat chart-click filtering and URL propagation as explicit interactions with defined targets and reset behavior. Sources: Grafana “Variables” and “Filter and Group by”; Metabase “Dashboard filters” and “Linked filters”; Tableau “Filter Actions.”
6. **For data changed elsewhere, freshness and write safety are separate decisions.** Focus/reconnect refresh reduces stale views when users return; polling bounds staleness while active; push can signal a change sooner, but needs connection status and a recovery/refetch path. Conditional writes prevent silently overwriting a newer version. Sources: TanStack Query freshness/polling docs; Supabase Realtime troubleshooting; MDN “HTTP conditional requests.”


### 1.2 Component, state, and data boundaries

- **Source finding — components can follow meaningful UI/data responsibilities, with separation earned by complexity.** React starts from a screen, divides it into a component hierarchy, and separates interactive state from derived display values; a small table header can remain with its parent until sorting complexity warrants a boundary. (React, “Thinking in React,” lines 40–70, 169–177.)
- **Source finding — chart panels can bundle a visualization with its query/configuration and controls while keeping data shaping identifiable.** Grafana describes source → query → optional transformations → panel; library panels allow shared definitions, with edits propagating and unlinking providing a local fork. A plugin visualization can be replaceable inside a separate panel/configuration shell. (Grafana “Dashboards overview,” lines 59–87; “Panel overview,” lines 32–57; “Manage library panels,” lines 32–58, 80–98; “Anatomy of a plugin,” lines 119–134.)
- **Synthesis — useful boundaries include screen/route, reusable panel, field group, and data query, but sources establish no universal component size or app-specific decomposition.** Do not infer that query logic must live inside the chart renderer or that every dashboard needs a plugin architecture.
- **Source finding — local state, lifted shared state, and centralized stores are alternatives with different coordination costs.** React describes local state, derived values, and moving shared state to a common parent; Vue describes a progression from component state to shared singleton/store, with per-request store creation needed under SSR; Redux documents a global store but also says temporary form values may stay local. Zustand and RTK Query document hook/selector stores and a distinct remote-data cache concern. (React “Managing State,” lines 114–181, 245–298; Vue “State Management,” lines 124–179, 310–326; Redux Essentials Parts 1 and 3, lines 69–73, 158–160; Zustand `create`, lines 53–76; RTK Query Overview and cache behavior.)
- **Synthesis — keep server-owned data, ephemeral view controls, and in-progress form edits conceptually separate even if a framework combines their code.** The sources distinguish these concerns; they do not establish one correct store or library.
- **Source finding — route loaders/actions and client fetching represent different ownership shapes.** Next.js describes colocated server-component fetches, request memoization and streaming; SvelteKit exposes route `load` data and re-runs it on URL/parameter changes while preserving component state; Remix forms/actions revalidate route data after submission and fetchers can submit without navigation; Vue/Nuxt documents reactive bindings and SSR handoff. These sources describe framework behavior, not comparative superiority. (Next.js “Fetching Data,” lines 136–167; SvelteKit “Loading data,” lines 136–153, 2825–2871; Remix `<Form>`, lines 82–98, and `useFetcher`, lines 106–145, 194–201; Vue “Form Input Bindings,” lines 134–146, 439–443; Nuxt tutorial, lines 9–40.)

### 1.3 Long forms and machine-assisted review

- **Source finding — a machine-assisted review surface can pair the source document with extracted fields and distinguish machine validation from human confirmation.** Rossum shows a document beside fields, points reviewers to unchecked/red-flagged items, and permits correction by selecting source text/bounds or typing. (Rossum “Getting Started with Rossum,” lines 72–89.)
- **Source finding — machine, human, and review-needed states can be represented separately, and thresholds route review effort.** Rossum documents field validation states and queue-level confidence thresholds; AWS says confidence and use-case sensitivity can route low-confidence values to closer human scrutiny, with thresholds depending on the application. (Rossum “Guide to Automation Process,” lines 40–59, 62–105; AWS Textract “Best practices,” lines 39–44.)
- **Source finding — one evaluated suggestion pattern offers candidate values for a person to choose, rather than silently committing predictions.** LAFF predicts categorical values, applies an endorsement heuristic, then presents accepted candidates; its authors mention semantic sections as a possible compromise for large forms but did not evaluate that layout. (LAFF, pp. 1–2, 12, 17.)
- **Adjacent source finding — an inspect, correct, apply, submit sequence exists for machine-generated labels in training-data annotation.** This is an AWS model-training workflow, not a normal business form. (Textract “Annotation and verification,” lines 78–109.)
- **Synthesis — a plausible form structure is a sectioned field editor that records source/provenance and review status, preserves person edits during refresh, and provides a deliberate confirm/submit step.** The complete extraction-prefill confirmation flow itself is not directly established by these sources; label this as an inference. Confidence scores and vendor validation colors do not prove correctness.
- **Source finding — asynchronously loaded defaults and dirty-field preservation are available form-state mechanisms.** React Hook Form documents async `defaultValues`, reactive `values`, and `keepDirtyValues`; Zod documents parse/safe-parse validation results. The issue report describes index-based dirty paths corrupting reordered arrays and over-preserving nested objects under refresh. (RHF FAQ, lines 239–293, 409–427; Zod Basics, lines 23–67; RHF issue #13627, lines 134–176.)
- **Synthesis — a long form can separate fetched initial values, machine suggestions, user edits, validation errors, and submission state; the data model should identify fields stably if arrays can reorder.** RHF docs do not establish a page/section architecture, and one issue report is not evidence of prevalence.
- **Counterweight — machine assistance leaves correction and transfer work, and confirmation boundaries can have consequences.** G2 reviewers report incorrect extraction, extra manual adjustment for complex layouts, and occasional failure to transfer data to the core system; one reviewer says they could not return after confirming without first saving a spreadsheet copy. Other reports describe residual manual cleanup or downstream mapping work. These are self-reports, mostly dated, commercially interested, or about adjacent workflow stages; they do not measure representative correction time or failure rates. (G2 “Rossum Reviews,” lines 345–366, 557–594, 692–730, 734–780, 782–814, 895–906; Reddit r/Accounting “Best approach for automated invoice parsing?,” lines 54–67; Reddit r/Accounting “what is the best OCR for invoice processing?,” lines 42–48.)

### 1.4 Boards, drag, and consequential changes

- **Source finding — the same drag gesture may mean reordering or a state transition.** Jira documents within-column rank movement separately from cross-column transition; Linear documents dragging between groupings as changing the grouped property and manual order as shared workspace-wide. (Jira “Monitor work in a kanban space,” lines 680–708; Linear “Display options,” lines 75–102.)
- **Source finding — workflow constraints may require a transition form or reject a drop.** Jira documents required fields, conditions, validators, permissions, multiple statuses per column, and failed-transition indicators. Jira Cloud support describes a move warning when the exact status transition is missing. (Jira “Transition an issue,” lines 704–727; Jira Data Center “Transitioning an issue,” lines 114–130; Jira Cloud KB, lines 5–39.)
- **Source finding — drag preview, committed local state, and fetched data should be treated as separate states.** dnd-kit shows temporary sorting and cancel restoration, and warns that a refetch during drag can replace data and create duplicates; its example defers synchronization until drag ends. React `useOptimistic` describes temporary updates that return to the current base state after failure. (dnd-kit “Managing Sortable State,” lines 109–120, 244–297; React “useOptimistic,” lines 154–160, 182–209, 247–273.)
- **Synthesis — for a consequential transition, a candidate flow is drag preview → eligibility/required-field step → server request → accepted placement or restored placement with an error.** Evidence supports these component parts, but no source evaluates this exact end-to-end flow or says when optimistic placement is preferable.
- **Weak counterweight — a Jira issue documented a mismatch between highlighted drop target and committed status, later marked fixed.** It shows a reported feedback/commit discrepancy, not a current or general defect. Atlassian community discussions were found but could not be opened, so no practitioner community evidence is available. (JRACLOUD-98383, lines 50–94; collection B “Not consulted.”)

### 1.5 Large lists, URL filters, and selection

- **Source finding — list processing belongs either in the browser over the loaded dataset or on the server over the full result set.** Sorting/filtering a server-paginated slice only affects that slice; filtering, sorting and pagination should use a consistent processing boundary. In server mode, query state feeds requests, pages may need reset when filters change, stale responses must not replace newer ones, and stable backend IDs support selection across responses. (TanStack Table “Client-Side vs Server-Side,” lines 198–269 and “Typical Server-Side Data Flow.”)
- **Source finding — URL query parameters can encode list state for navigation and shareability.** Next.js page `searchParams` covers filtering, pagination and sorting; its Form component serializes named GET inputs into search parameters. Grafana also syncs variables to URL parameters, with an option not to expose them in links. (Next.js “page.js,” lines 155–203, 243–269; Next.js “Form Component,” lines 109–144, 169–218; Grafana “Variables,” lines 104–120.)
- **Source finding — saved views can package reusable criteria and view-specific presentation.** Shopify documents saving, renaming and duplicating views, with criteria that can include matching future records; some resource lists allow configurable columns scoped to the current view. This fits recurring operational slices where people revisit the same criteria or need different columns by task. It is a Shopify product pattern, not evidence that saved criteria should always be dynamic or that every list needs per-view columns. (Shopify “Searching and filtering your lists using views,” lines 14–20, 71–88, 105–120, 138–209.)
- **Source finding — selection scope should be explicit when actions can span pages or filtered results.** Shopify distinguishes individual rows, ranges, the current page, all store items, and all results matching filters; filtered sets over 50 can require a separate “Select all results” step. Actions vary by resource, prominent actions can sit separately from overflow actions, deletion asks for confirmation, and longer operations may take time. This suggests that selection scope and execution status are distinct interface states; the source does not establish whether users always understand the scope or guarantee completion, rollback, or recovery. (Shopify “Using bulk actions,” lines 5–10, 18–62.)
- **Source finding — cross-resource search can stage results from broad discovery into grouped, sortable lists.** Stripe documents immediate top results followed by expanded/grouped results with sortable columns, plus identifier/date lookup and field/operator filters, terms and exclusions. This fits finding records across several business objects; it does not establish saved views, bulk actions, live updates, or general usability. (Stripe “Perform searches in the Dashboard,” lines 10–25, 26 onward, 93–120.)
- **Counterweight — bulk operations can diverge from the selection affordance or disrupt an established workflow.** One Shopify merchant reported a bulk deletion that did not complete for 60,000 products; another described disruption after a bulk-editor workflow changed. These are individual merchant reports and do not establish reproducibility, current behavior, objective usability, or system limits. (Shopify Community “How can I quickly batch delete all products in my store?,” lines 22–57; “Why has Bulk Editor…,” lines 8–42.)
- **Synthesis — list structure should expose query state, result scope, selection identity, and action confirmation as separate concerns.** Virtualization affects rendering, not transfer/filter semantics; it is a composable viewport structure for lists, boards and grids. (TanStack Virtual “Virtual,” lines 215–239.)

### 1.6 Dashboards and charts

- **Source finding — dashboard controls can be global, tab/header-level, card-level, or linked/cascading, but their connections are explicit.** Metabase distinguishes filters (change displayed data) from parameters (change presentation), requires filter-to-card field mapping, and supports parent-child linked filters where metadata relationships allow it. Grafana variables are reusable in queries, titles and links; only elements configured to use them update. (Metabase “Dashboard filters,” lines 385–407, 520–532; “Linked filters,” lines 367–397; Grafana “Variables,” lines 36–57, 67–87.)
- **Source finding — apply behavior and interaction targets are structural choices.** Metabase supports auto-apply or an explicit Apply step, default/required filters, personal filter state, and chart-to-filter cross-filtering. Tableau filter actions specify source, trigger, target sheets, field mapping and what clearing a selection does. Grafana supports dashboard filters, panel drilldown and links carrying context, with datasource/configuration constraints. (Metabase “Dashboard filters,” lines 644–714; “Dashboard interactivity,” lines 439–455; Tableau “Filter Actions,” lines 7–56; Grafana “Filter and Group by,” lines 81–125, 186–195.)
- **Synthesis — global filters fit genuinely shared analytical context; narrower controls reduce accidental scope, and cascading choices can constrain dependent options.** This is inferred from product structures, not a comparative usability finding. A required/default filter is not evidence of authorization enforcement.
- **Source finding — chart panels commonly separate data acquisition/shaping, visualization, and panel options; chart sizing follows its container lifecycle.** Grafana provides the panel composition model; ECharts documents resize handling via window events or `ResizeObserver`, and dispose/reinitialize when chart containers are removed/recreated. (Grafana “Panel overview,” lines 32–57; ECharts Handbook “Chart Container,” lines 28–69.)
- **Bounded counterweight — two Recharts reports show container sizing and resize behavior can depend on parent layout and version.** One report for Recharts 2.7.2 described static dimensions in a fixed-parent/editor layout; the issue shows no final fix, and the reporter later identified static parent width as a factor. A long-running report includes resize and flex-layout complaints across versions, but a maintainer committed a fix in July 2025 and closed it as completed. These anecdotal reports do not establish prevalence, a current general defect, or that every layout combination is fixed. (Recharts issue #3688, “ResponsiveContainer not working when a fixed parent is specified”; issue #172, “ResponsiveContainer does not respond to resizing from large to small.”)
- **Source finding — chart construction makes data identity and visual encoding explicit.** D3 joins data to rendered elements through enter/update/exit sets and supports keyed identity so a mark can follow a record instead of relying on array position. Observable Plot describes marks with channels such as x, y or color mapped through scales from data domains to visual ranges; type inference assumes consistently typed values and may require explicit conversion during loading. These are low-level construction models, not a recommendation to adopt either library or a dashboard-level architecture. (Observable, “D3 selection: Joining data,” lines 251–274, 307–343, 370–401; Observable Plot, “Scales,” lines 166–170, 562–587, 804 onward.)
- **Counterweight — a Grafana user reported URL variables changing without dependent data refreshing in version 11.5; a separate issue reported stale dependent panels in 11.4 and was auto-closed without shown fix.** These are version-specific reports, not prevalence evidence or proof of current behavior. (Grafana Community “Dashboard variables in URL do not trigger data update in Grafana 11.5,” lines 3–18; Grafana issue #108426, lines 129–177, 231–247.)
- **Counterweight — a separate Grafana report described an ad hoc filter failing to propagate when a datasource variable selected the datasource; a maintainer said it was fixed and backported to 10.1.x.** This is a resolved, version-specific coordination failure, distinct from the reports without a shown fix above; it does not establish an ongoing defect. (Grafana issue #74657, lines 155–179, 204–245.)
- **Bounded counterweight — an ECharts issue roundup links dataZoom reports involving multiple-axis/legend synchronization, slider/toolbox conflicts, and jumpy panning on large series.** It signals edge cases in interactive chart controls, but is an issue-author roundup rather than a systematic study; it does not establish frequency, severity, current status, or independent reproduction. (Apache ECharts issue #20392, issue body.)

### 1.7 Server changes, freshness, and stale writes

- **Source finding — refresh-on-focus/reconnect, polling, and push are distinct update structures.** TanStack Query refetches stale data on mount/focus/reconnect; polling runs on an interval independent of `staleTime`. Supabase documents Broadcast and Postgres Changes, with differing setup/scaling trade-offs. (TanStack Query “Important Defaults,” lines 224–244; “Polling,” lines 220–261; Supabase “Subscribing to Database Changes,” lines 50–56, 226–232.)
- **Source finding — push events need status and recovery, and an event can be treated as a signal to refetch authoritative state.** Supabase troubleshooting documents readiness/configuration gaps and explicitly says Realtime does not guarantee delivery of every message; separate connection and subscription state are observable. Query invalidation can mark matching views stale and refetch active observers. (Supabase Realtime Postgres Changes Troubleshooting, lines 5–11, 318–367, 397–410; Supabase “Realtime Messages Not Arriving,” lines 5–55; TanStack Query “Query Invalidation,” lines 219–238.)
- **Source finding — cached/offline data can be labeled with freshness, while conflict policy may still be last-write-wins.** Firestore listeners expose `fromCache`; offline edits sync later and concurrent same-document edits use last-write-wins. (Firestore “Access data offline,” lines 445–459, 651–654.)
- **Counterweight — individual reports describe gaps after reconnect and listeners that appeared stale.** A Supabase client user reported missed events during reconnect on `supabase.js` 1.29.3; another Supabase discussion reports a roughly five-second resubscription gap and a respondent describes fetching initial/missed data after connection. A Firestore JS SDK issue reporter described missed server changes on a brittle network and no later catch-up, but could not reproduce it on demand; the issue was marked “Repro Needed.” A separate Firestore Admin Node report described a server-side listener stopping after a connection loss on old Node/Firebase/Admin SDK versions, so it is not evidence about current browser listeners. These are product/version-specific reports, not prevalence evidence or proof of a current general defect. (Supabase Realtime client issue #133, lines 175–190; Supabase discussion #35926, lines 137–157; Firestore JS SDK issue #8903, lines 180–187; Firestore Admin Node issue #119, lines 130–169.)
- **Source finding — version-conditional writes reject stale updates.** MDN describes `If-Match`/`If-Unmodified-Since` and `412 Precondition Failed`, after which a client can reload or show a diff for user reconciliation. (MDN “HTTP conditional requests,” lines 263–276; “412 Precondition Failed,” lines 172–174, 198–213.)
- **Synthesis — freshness mechanisms do not by themselves resolve unsaved form edits; writes need an explicit stale-version rule.** Polling/focus refresh are simpler but delayed; push is more immediate but must account for disconnects and recovery; conditional writes protect against silent overwrite but leave merge/review UI to the application. This synthesis is supported by the sources’ stated limits, not a measured comparison.

### 1.8 Where sources diverge

- **Suggestions versus prefilled-value confirmation:** LAFF evaluates candidate suggestions chosen by the person; Rossum documents extracted values with machine/human validation marks and correction; AWS Textract’s inspect/correct/apply/submit example is for training annotation. They do not establish one general best confirmation flow for extraction-prefilled business forms. (LAFF pp. 1–2, 12, 17; Rossum “Getting Started,” lines 72–89; Textract tutorial, lines 78–109.)
- **Optimistic versus accepted-first board movement:** dnd-kit and React document optimistic local presentation and rollback mechanics; Jira documents server-governed constraints, required fields and failed transitions but does not say whether to move cards optimistically. No evidence compares user outcomes for accepted-first versus optimistic transition UX. (dnd-kit “Managing Sortable State”; React “useOptimistic”; Jira “Transition an issue.”)
- **Client versus server list processing:** TanStack describes both and says the choice depends on transfer, query, browser, and interaction costs; no source supplies a universal row-count cutoff or product-specific profile. (TanStack Table “Client-Side vs Server-Side,” lines 198–243.)
- **Server freshness:** periodic refetch, focus refresh, and subscriptions solve different timing/complexity problems; the collection offers implementation docs and anecdotal failure reports, not a head-to-head reliability or latency evaluation. Supabase and Firebase reports concern different products, versions, and conditions.
- **Filter scope:** Grafana, Metabase, and Tableau expose global/shared, narrower, linked, and chart-driven structures. None offers independent evidence that one scope is generally easier or safer; product docs describe capability and constraints.

### 1.9 Which choices are easy or hard to reverse

The distinction below is a **cross-source inference**, not a migration-cost measurement.

- **Usually more reversible at the UI/data-flow level:** component boundaries; local versus lifted/shared view state; chart panel composition; client versus server list-processing ownership when query state and request contracts are explicit; refresh cadence/mechanism; drag preview/rollback mechanics. These can often be changed without changing the meaning of persisted records, though the sources do not measure the actual migration effort.
- **Less reversible once shared or persisted:** status/workflow meanings; whether a drag changes rank or a business status; shared manual order; stable record identity; server filtering and pagination contracts; filter-to-field mappings used by saved/shared dashboards; conditional-write/version rules; machine-versus-human confirmation state and what “confirmed” means. Changing these can alter stored data, server/API behavior, shared views or user-visible meaning. This is inferred from their documented role in persistence, workflow constraints and shared state.
- **Decision implication — lock the semantics and server contract before optimizing component arrangement.** The sources support this ordering as a synthesis: view composition can be refactored, while persisted/shared meaning is more consequential to change.

## 2. Weak points and suggested next step

- **Machine-prefilled long forms remain the largest evidence gap.** The collection has Rossum product flows, LAFF suggestions, confidence-routing guidance, and Textract training annotation, but no direct independent study or evaluated product example of an end-user reviewing and confirming extraction-prefilled values in a long business form. Correction-time evidence is self-reported, vendor-published, or about adjacent workflows; no representative correction effort or missed-extraction rate is established.
- **Component/chart structures are mostly vendor/framework descriptions.** Grafana supplies a detailed panel model and React supplies general component decomposition, but there is no independent comparison of reusable chart boundaries or evidence that the same composition fits a custom business app.
- **Board counterweight is limited.** Jira public issue evidence and Atlassian support reports exist, but the requested community discussion pages could not be opened; no usable community discussion was consulted. Drag state docs are library guidance, not an evaluated business workflow.
- **Server-change evidence lacks comparative measurement.** Polling, focus refresh, push, cache reconciliation and conditional writes are described, but there is no cross-system benchmark of freshness, missed-event rates, implementation cost, or conflict-resolution UX. User reports are anecdotal and version-specific.
- **Dashboard reports do not establish prevalence.** URL/filter mismatch reports are isolated version-specific cases. Vendor docs show wiring and scope, not cross-product usability or reliability.
- **Other constraints intentionally remain outside this digest:** what a state change triggers belongs to Business logic; indicator choice belongs to Metrics and reporting; performance and accessibility belong to Frontend experience; UI-library selection is out of scope. The chart accessibility sources in the collection are excluded from the main synthesis and retained below as annex material.
- **Collection review notes:** round 3 review of collection a passed after board and server-change sources were added. Collection b was escalated because no direct end-user extraction-prefill confirmation flow was found; its two prior reviews noted weak component/chart composition and a missing Jira community counterweight. Collection c’s round 1 review found dashboard filters under-collected and accessibility evidence out of scope; round 2 passed after filter-scope, chart interaction, and independent responsive-container evidence were added. Carry the machine-form gap and unavailable Jira community evidence forward rather than treating those concerns as resolved.

**Suggested next step (the writer's inference from the weak points).** The largest gap is the interaction for confirming machine-prefilled long forms, where no independent source evaluates an end-user flow. It is the natural seed of a narrow objective that crosses this area and Applied AI, to be run after Applied AI says what the machine produces and how it flags its own uncertainty. The rest of the gaps (board optimism, freshness, chart composition) are comparative evidence that the sources do not contain, and they can be settled by a prototype in the app more cheaply than by more research.
