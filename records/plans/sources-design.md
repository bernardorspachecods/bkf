# Sources registry design

Design in progress, settled with Bernardo one decision at a time. When it is built, each decision moves to the document that owns it and this file is removed.

## Intent

Agents research the web (docs, posts, talks, packages, repos) for software work across many repositories. Sources end up scattered across conversations, the same ones are reopened, and metadata (author, publication and consultation dates) is lost. The registry makes every source researched once: an agent checks it before searching and records what it reads mechanically, so metadata cannot be forgotten.

First consumer and test case: `~/software-factory/fontes.md` (F01–F14), organized by the session that organizes that library.

## Decisions taken

1. **One store for the whole machine**, its own git repository at `~/sources/`. It holds one record per source: identity, metadata, what it says, and whether it was used or discarded. Each consuming bundle keeps only its citations (which practice a source supports and why), pointing to global ids. Relevance is the consumer's, never the record's.
2. **Format and ids.**
   - One folder per source: `records/<id>/<id>.md` (a BKF document, metadata in frontmatter) and `<id>.txt` (a text snapshot of the page, read instead of reopening it; kept out of git).
   - The id is readable, `<org-or-author>-<short-title>` in kebab-case (`notion-ratcheting-eslint`), generated by the `add` command. No year: publication dates are often unknown. While a record is `pending`, `finish --id` may rename it, because `add` builds the id before an agent can correct a wrong author or title (the migration produced `ai-ai-engineer`, `atlassian-unknown`); after `finish` the id never changes. `add` never puts `unknown` or a generic host word in an id.
   - Deduplication is by normalized canonical URL, not by id: `add` refuses a known URL and returns its id.
   - Redirects: a redirect to the same page (only what normalization folds) stores the final URL; a redirect to another page keeps the requested URL as `url`, records the final one in `redirected_to`, and warns, because the cited page may be gone (the migration's F04 landed on a generic page). Meta-refresh and simple script redirects are followed once.
   - Known limitation: `updated` can be a build date the site regenerates (F10 showed the consultation day); there is no reliable way to tell.
   - Accepted risk: snapshots are lost on another machine.
   - When `add` gets no text (a script-rendered page, an HTTP 403, a manual record), the agent saves the text it read by another path (the rendered page, the package README) with `bkf sources snapshot <id> --from <file> --note <where it came from>`, which marks `snapshot: manual`. Key claims anchors are always checked against a snapshot: `finish --status used` refuses a record with no snapshot, and `check` reports it as an error. Settled on the migration, where F03 and F06 had claims nobody could verify.
3. **Fields and discarded sources.** `add` tries to extract every field and writes `unknown` when it finds nothing, so `unknown` means "looked, not there"; an empty field is a `validate` error. This replaces the `?` of `fontes.md`, which mixed "absent" with "never checked".

   | Field | Required | Filled by |
   | --- | --- | --- |
   | `id`, `url` (canonical) | yes | `add` |
   | `title` | yes | `add`, from meta tags or `<title>` |
   | `author` (person or org) | yes, or `unknown` | `add`, from JSON-LD, meta `author`, or the domain as org |
   | `published` | yes, or `unknown` | `add`, from JSON-LD `datePublished` or `article:published_time` |
   | `updated` | no | `add`; matters for docs pages, which change |
   | `consulted` | yes | `add`, stamped automatically; a later consultation appends a date |
   | `type` | yes | `docs`, `article`, `talk`, `package`, `standard`, `repo`, `paper` or `thread`; inferred by `add`, corrected by the agent |
   | `via` | yes | How the source was reached: the search query, another source's id, or `user` |
   | `status` | yes | `pending` (set by `add`), then `used` or `discarded` (set by the agent with `finish`) |
   | `description` | yes | The agent: what the source is about, in one line; it becomes the catalog row |
   | Key claims | yes when `used` | The agent, each with a verbatim anchor |

   Discarded sources:
   - Global, in the record: `status: discarded` with a `reason` from a fixed list: `dead`, `paywall`, `copy-of:<id>`, `marketing`, `outdated` (only clear cases, such as a discontinued API). These are facts about the source, valid for every consumer, and such a record is never reopened.
   - "Not useful for this" stays in the consumer's citations table with its reason: a source irrelevant to one repository may serve another.
   - Accepted: extraction of `author` and `published` fails on many docs sites, so many fields will read `unknown`; they are honest and dated.

4. **Lookup before researching**, mechanical first because an agent's memory is what failed for the dates.
   - A `PreToolUse` hook on `WebFetch`: a registered URL (normalized as `add` does) is denied, with a message naming its id and its `<id>.txt` to read instead.
   - A `PreToolUse` hook on `WebSearch`: the top 5 registered sources for the query are injected as context.
   - Reopening a source on purpose goes through one explicit command, `bkf sources complete <id> --why <reason>`: it records the reason in the record and opens a 30-minute window during which that URL passes; the fetch then re-extracts the metadata, fills the fields and appends a consultation date. A second attempt without it is denied again, because agents retry denied calls by reflex and the hook cannot see an agent's mission.
   - When `<id>.txt` is missing or empty, the hook warns and lets the fetch pass: there is no copy to read.
   - Planning by hand uses `bkf search <topic> --cwd ~/sources`, as in the thesis library.
   - To verify when built: that the hook fires in subagents, where most research happens, and what Codex offers for its web tools (until then, Codex has only the manual lookup).
   - URL variants: normalization covers tracking parameters and trivial differences; versions of a docs site stay separate sources on purpose.

5. **Capture while researching**, by hooks, leaving the agent only what needs judgment.
   - A `PostToolUse` hook on `WebSearch` appends the query, date, session and returned URLs to `searches/<date>.jsonl`. The `WebSearch` lookup of decision 4 also reports a repeated query: when and in which session it ran, and what it returned.
   - A `PostToolUse` hook on `WebFetch` of a new URL runs `bkf sources add <url>`. The script fetches the raw HTML itself, because `WebFetch` returns a model's summary and the dates and author live in the HTML (JSON-LD, meta tags). It extracts the fields or writes `unknown`, stamps `consulted`, sets `via` to the session's last search query, writes `<id>.txt` and sets `status: pending`.
   - The agent closes the record with `bkf sources finish <id> --status used|discarded`, adding the description, and the Key claims or the reason.
   - A `Stop` hook lists the `pending` records the session created and asks the agent to close them.
   - Not captured: `curl` in a shell, the browser and MCP fetch tools. Accepted, since agents research almost always through `WebFetch`.
   - A page the script cannot read (JavaScript, blocked) gives a record with `unknown` fields and no snapshot; by decision 4, the next fetch passes.
   - To settle when built: concurrent sessions contend for the git lock of `~/sources/`; files never conflict, but committing needs a retry or a periodic commit instead of one per `add`.

6. **Migration of `~/software-factory/fontes.md`**, the real test, once `add` exists.
   - F03–F13 have URLs: `bkf sources add <url> --via migration:software-factory`; reopening the pages tries to fill the `published` and `author` that read `?` today. The column of the claim each supports becomes the `description` and Key claims.
   - F14: find its URL (most likely `github.com/imbue-ai/ratchets`), then `add`.
   - F01 and F02 are known only through the summary `~/to-review/agent-engineering.md`: search for their original URLs; failing that, `--manual` records with `url: unknown`, outside deduplication, which the record states.
   - The old consultation date ("≤ 2026-11-19") is not invented: `consulted` gets the migration date and the record notes an earlier consultation with its date lost.
   - Split of work: this session builds and migrates the records in `~/sources/`, then sends the `Fnn → id` map to the session that organizes the library; that session rewrites `fontes.md` as a citations table (`global id | what it supports here | used in`, plus local discards) and the practices' citations, because the bundle is its own.
   - Success measure: how many `?` become real values; the remaining `unknown` measure how often extraction fails.
7. **The code lives in `bkf`**, because it uses BKF's validation, search and hook installation: a `bkf sources` command (`add`, `complete`, `finish`) in `bkf/tooling/`, its hooks installed by `bkf hooks`. `~/sources/` holds only data.

## State of the build

Built in units by Codex `gpt-6.2-sol`, reviewed by the coordinating session; `~/sources/` created and F01–F14 migrated by a Sonnet agent (hand-off: `records/plans/sources-migration-map.md`). Two reviews by Codex `gpt-6.2-astra` found blockers (no public-network boundary in the fetcher, unbounded responses, redirect destinations merged into other sources, refresh able to erase evidence, one malformed record disabling capture, page text read as a section heading); all were fixed, and a third review by Opus 5.5 found the result ready to install, after which its remaining should-fix findings were fixed too. Still to do: install the `sources` hooks, watch them fire in a live session and in a subagent, and have the library's session rewrite `fontes.md` from the migration map.

Known gaps, deferred on purpose:

- Hook latency grows with the store: each call parses every record and rebuilds the search index (about 150 ms per call with 14 records). Build incremental indexes for URLs, search history and pending ownership when it is felt.
- A process killed mid-write (rename, add) can leave a half-moved folder; exception rollback does not run on process death.
- When a commit fails after its retries, a later commit can include a catalog row whose record file is not committed.
- Path containment does not cover a symlinked `records/` or `.txt`.

## Taken from the thesis library

`~/data-science/library/` is a separate system for the thesis; it is not merged, only learned from.

| Thesis library | Here |
| --- | --- |
| One file per source, created only by `library.py add` | Same: `add` is the only way in, and it extracts metadata and stamps the consultation date |
| Text snapshot `<id>.txt`, searched instead of rereading the source | Same |
| Key claims with a verbatim anchor, checked by `check` | Same, lighter: `sec.` locators, no pages |
| Relevance owned by the consumer, not the record | Same, see decision 1 |
| Identity from OpenAlex or a DOI | Not available on the web: canonical URL plus the page's meta tags and JSON-LD |
| Id `author-year` | Replaced, see decision 2 |
| Mandatory method appraisal | Dropped: too heavy for docs and posts |
