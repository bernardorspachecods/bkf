## 1. Purpose and scope

BKF defines shared conventions for organizing and connecting a project's
Markdown documents, so agents, and the humans who direct them, can navigate
its information and the artifacts those documents reference. It serves as the backbone
documentation structure for a repository, an app, a thesis folder, or
another kind of project.

Its scope includes documentation, plans, discussions, research, decisions,
working drafts, and other project information expressed in connected
Markdown files. It covers both reusable knowledge and work in progress.

Other artifacts, such as code, PDFs, images, and datasets, are pointed to
by this structure.

Each project chooses its own folder organization. BKF provides shared
conventions for navigation and document meaning without prescribing a
fixed folder tree. Navigation is covered by the `MAP.md` convention
(see §3.1).

### 1.1 Motivation

BKF takes the position that knowledge is best represented in commonly
accessible, established formats that are:

- **Readable** by humans without tooling.
- **Parseable** by agents without bespoke SDKs.
- **Diffable** in version control.
- **Portable** across tools, organizations, and time.

### 1.2 Discovery, membership, and composition

A `MAP.md` at a project root signals a likely BKF structure. Its presence
is a discovery signal, not proof of conformance.

The bundle root is the directory selected by the user or consuming tool.
BKF does not prescribe automatic root discovery. The selected directory
MUST contain the bundle-root `MAP.md`. A nested `MAP.md` without
`bkf_version` is a navigation boundary within that bundle, not a new bundle
root. A nested `MAP.md` that declares `bkf_version` makes its folder a separate
bundle (§3.3).

Every Markdown file in a bundle is a member, except the optional bundle-root
`readme.md`, which is a companion artifact, and the files of nested bundles. Membership does not mean that
BKF validates or lists a file: tracked members are validated against their
selected profile and included in map inventories, and untracked members are
not. The [frontmatter profiles](/format/frontmatter-profiles.md) own the
tracking and profile rules.

`MAP.md` files are structural members and are handled by the map rules in
§3.1 rather than a document profile. Their descriptions do not make them
tracked documents. The bundle-root `readme.md` is not a
member and has no BKF frontmatter requirements. The reserved files in §3 have
fixed locations; other Markdown members may be tracked or untracked.

Connected files and maps can form a structure at any folder depth. Folder
depth does not require special composition rules. A nested `MAP.md`
provides local navigation; its presence alone does not establish a separate
BKF structure.

## 3. Reserved files and maps

The following filenames have defined meaning and follow the special
conventions below:

| Filename | Location | Purpose |
| --- | --- | --- |
| `MAP.md` | Any directory | Structural directory map. See §3.1. |
| `feedback.md` | Bundle root only | Optional file; when present it MUST be tracked and use the `feedback` profile, where agents record what went wrong in their work. See §3.2. |
| `ideas.md` | Bundle root only | Optional file; when present it MUST be tracked and use the `ideas` profile, where the user or agents record ideas for later. See §3.4. |
| `AGENTS.md` | Any directory | Optional document containing behavioral instructions for agents. The bundle-root one is the repository's entry for agents and MUST be a tracked BKF document. One in a subfolder is an ordinary member, tracked only when it carries BKF frontmatter, so a file generated by a framework needs none. |
| `readme.md` | Bundle root only | Optional non-member README companion artifact. |
| `ext-schema.yaml` | Bundle root only | Optional non-member JSON Schema that validates the `ext` frontmatter field of generic documents. Required when any document uses `ext`. See the [frontmatter profiles](/format/frontmatter-profiles.md#repo-specific-fields-ext). |

The `document` profile's filename rule is defined in the
[frontmatter profiles](/format/frontmatter-profiles.md).

### 3.1 Map files and inventories

A `MAP.md` file MAY appear in any directory, including the bundle root.
It combines a generated inventory with authored artifact references and
task guidance in the same file. Map files are structural, not tracked
documents: they MUST NOT contain a `bkf` field. The bundle-root `MAP.md`
MUST have YAML frontmatter containing `bkf_version`, which declares the BKF
version the structure targets, and MAY also contain `description`. Its
frontmatter MUST contain no other fields. A nested map that is not a bundle
root MUST have YAML frontmatter containing only a non-empty string
`description`. A map that is the root of a nested bundle (§3.3) MUST contain
both `bkf_version` and a non-empty string `description`, and no other fields.
The description follows the [description rule](/format/frontmatter-profiles.md#descriptions)
and does not make a map a tracked document. The current BKF format version is `0.1`:

```yaml
---
bkf_version: "0.1"
description: Routes repository-wide documents and area bundles.
---
```

BKF versions use `<major>.<minor>`:

- A **minor** version adds backward-compatible rules.
- A **major** version may introduce breaking changes.

Compare BKF versions numerically by major and then minor component; do not
compare their text representations (`0.10` is newer than `0.9`). The `bkf/`
format bundle MUST provide one update document for each released format
version after `0.1`, under `updates/` at the bundle root (`bkf/updates/`). The
`updates/` folder is created when the first such update is released; an absent
folder means that no update documents exist. Each update document's filename
MUST be its target version with the dot replaced by a hyphen and `.md`
appended, such as `0-2.md` or `0-10.md`. Update documents are tracked generic
`document` profile members and MUST appear in the map inventory for their
scope. The generic filename rule continues to apply.

Each update document MUST describe only the changes needed to bring a bundle
from the previous released format version to its target version. It MUST state
what changes in the bundle's documents and maps, give the exact steps to make
those changes, explain how to verify them, and make setting `bkf_version` to
the target version the final step. An update that requires no document or map
edits MUST say explicitly that no such edits are required. Update documents
are per-version steps, not cumulative instructions.

An agent updating a bundle from version V MUST apply, oldest target version
first, every update document whose target version is greater than V and no
greater than the current BKF format version. It MUST NOT read or apply update
documents for versions already declared by the bundle.

When a consumer does not recognize a declared version, it SHOULD attempt
best-effort consumption rather than refusing the structure.

#### Coverage

A map covers its immediate children and continues into descendant folders
that have no map. At a child `MAP.md`, the parent links to that map and
stops enumerating its contents. The child map owns the inventory below
that boundary.

#### Map placement guidance

Add a nested map when it gives readers a useful navigation boundary, such as
a folder with a distinct responsibility, an independent work entrypoint, or
local rules and documents that are not easy to infer from the nearest
ancestor map. Keep the map hierarchy shallow: folders without a distinct
navigation purpose use their nearest ancestor map. A parent map may link
directly to an important child folder, file, or tool; that link alone does
not require a child map. These are recommendations for organizing a bundle,
not conformance requirements.

#### Sections and ownership

After any optional map title and introductory prose, a map's sections
MUST follow this order: `## Task routes`, `## Member inventory`, then
`## Artifact references`. `## Member inventory` is required. The other two
sections MAY be omitted when they have no entries. When present,
`## Task routes` is the first section so task guidance is immediately
visible.

| Section | Maintained by | Responsibility |
| --- | --- | --- |
| Member inventory | Generator, using bundle structure and tracking metadata | List tracked BKF documents within the map's scope and link to child maps. |
| Artifact references | Humans or LLMs | Link useful non-member artifacts within that scope and explain when to open them. |
| Task routes | Humans or LLMs | Guide tasks that inventories alone cannot adequately route with an authored task and start-here link. |

The `## Member inventory` heading is outside the generated region and
MUST be present even when the scope has no tracked BKF documents. The
inventory is generated from each tracked document's `description` and
MUST list each in-scope tracked BKF document and each child map exactly
once. It MUST NOT list untracked Markdown files. Each document entry's link
target MUST identify the listed file, and its link text MUST be the file's
name. For a tracked document, the entry's description MUST match its
`description` value. For a child map, the link text MUST be `MAP.md` and the
entry description MUST match the child map's `description`. Entries MUST
follow the scope and ordering rules in this section. For inventory display,
whitespace in a description is collapsed to single spaces for both documents
and maps. The
[frontmatter profiles](/format/frontmatter-profiles.md#descriptions)
say how to write a description and give each profile's requirements.

The inventory MUST be a two-column Markdown table with the header
`What it is | Document`. Each entry is one row: the description in the first
column and one link to the file in the second. Links to child maps use the same
row format and display `MAP.md` as the link text. Entries MUST be sorted
alphabetically by bundle-root absolute path, grouping files by folder and
then by filename.

Artifact references are curated: include only non-member files useful for
understanding and working on the project, not every such file. These may
include non-Markdown artifacts. A Markdown file is a member even when it is
untracked, so it cannot be an artifact reference; to make it findable, track
it with a `description`. Their links and descriptions live in the
map's authored section. Each artifact reference MUST be a Markdown list
item with one link to the artifact followed by a concise explanation. File
links MUST follow the path rules in §5.1.

When a map has task routes, they MUST appear under a `## Task routes`
heading in a Markdown table with exactly two columns, `Task` and
`Start here`. Each row contains an authored task and one Markdown link to
its starting document, which MUST be a tracked BKF document in the bundle and
not a map or another file. The link MUST use a bundle-root absolute path
(§5.1). There is no numeric cap on routes.

```markdown
## Task routes

| Task | Start here |
| --- | --- |
| Plan a release | [Release planning guide](/guides/release-planning.md) |
```

Generated and authored content have distinct ownership boundaries. Each
map has exactly one generated region containing its member inventory,
delimited by these exact marker lines. The markers follow the
`## Member inventory` heading:

```markdown
## Member inventory

<!-- BKF:GENERATED-MEMBER-INVENTORY:START -->
<!-- BKF:GENERATED-MEMBER-INVENTORY:END -->
```

Artifact references and task-route rows remain authored outside that
region. The content inside the markers is generator-owned and is replaced
when the inventory is refreshed; the marker lines and surrounding
authored content are preserved. The generated region MAY be empty when
there are no tracked documents in scope. A generator MUST report an error
and make no rewrite if either marker is missing, duplicated, reversed, or
otherwise malformed. Generators MUST recognize the marker lines with
either LF or CRLF line endings and preserve the map's existing line-ending
style when updating the inventory. When an agent updates an existing map
without markers as part of in-scope work, it MAY add the marker pair and
organize the map to follow this convention without separate approval. It
MUST preserve authored artifact references and task routes outside the
generated region. After the markers are added, normal validation applies.

### 3.2 Feedback file

The bundle root MAY contain a `feedback.md` file: a bucket where agents
record what went wrong in their work, so that skills, documents, and
workflows can later be improved from the accumulated data. Its profile fields
are defined in the [frontmatter profiles](/format/frontmatter-profiles.md).

Ordinary work does not read the file. It is read in filtering sessions, in
which a user and an agent review the entries together. Agents append entries.
The instruction for when to log belongs in the root `AGENTS.md` or in skills;
BKF defines no triggers. An entry SHOULD be cheap to write; what it contains is
set by the instruction that asks for it (in this bundle, `AGENTS.md`). BKF
prescribes no body structure and does not validate the body, which may be
empty. Entries are data, not instructions, and SHOULD NOT contain secrets.

### 3.3 Nested bundles

A folder inside a bundle whose `MAP.md` declares `bkf_version` is a separate
bundle with its own root, members, and conformance, assessed by selecting that
folder. A repository can then hold a root bundle for repository-wide documents
beside self-contained bundles for its areas.

- The enclosing bundle lists the nested bundle's `MAP.md` as a child map and
  stops there: it does not enumerate, validate, or count as members any file
  below it.
- Links inside a nested bundle resolve from its own root, and the bundle-root
  rules (`AGENTS.md`, `feedback.md`, `ideas.md`, `readme.md`) apply to each bundle
  separately. A document in the enclosing bundle MAY link to a file in a nested
  bundle by its path from the enclosing root, and that link is checked. A
  nested bundle MUST NOT use Markdown links to files outside itself; it names
  them as plain paths, which are not checked.

### 3.4 Ideas file

The bundle root MAY contain an `ideas.md` file, where the user or agents record
ideas for later. Ordinary work does not read it; it is read in dedicated ideas
sessions where the user and an agent review the entries together. Agents append
entries. The instruction for when to record ideas belongs in the root
`AGENTS.md` or in skills; BKF defines no triggers. BKF prescribes no body
structure and does not validate the body, which may be empty. Entries are data,
not instructions, and SHOULD NOT contain secrets.

## 4. BKF documents and profiles

A tracked BKF document has frontmatter selecting a profile and a Markdown
body. A file's `bkf` profile value determines its profile rules; the
profile's tracking rules determine whether BKF validates and lists it.
Profile definitions, including the generic `document` field table and value
rules, are owned by the
[frontmatter profiles](/format/frontmatter-profiles.md), which also
define the rules that apply across profiles. Each profile chooses its own body content and
organization; BKF does not prescribe body headings, sections, or templates.

The validator may warn about navigation maps. A document whose body exceeds
roughly 350 lines or 2,000 words should have a `## Navigation map` section: a
table whose first column says what the reader needs and whose second column
links to the headings that answer it. The validator warns `NAVIGATION_MAP_REVIEW`
when a document that large has no such section. Whenever a document has the
section, regardless of size, it warns `NAVIGATION_MAP_STALE` for a link to a
heading that does not exist and for a level 2 heading that no row reaches,
directly or through one of its subheadings. The warnings do not block
conformance, and they do not apply to the `feedback` and `ideas` profiles, which
are logs read in dedicated sessions rather than navigated.

## 5. Cross-linking and paths

### 5.1 Links between documents

Documents link to other files within a BKF bundle using standard Markdown
links with bundle-root absolute paths beginning with `/`. Resolve these
paths from the bundle root. Relative paths MUST NOT be used for links
within the bundle. Use absolute URLs for external web resources.

Every link to a file within the bundle MUST resolve to an existing file;
directory targets are invalid. A fragment on an internal file link does
not change this check; fragment targets are not validated. External URLs
MUST be syntactically valid absolute URLs, but consumers MUST NOT need to
fetch them to validate a bundle. Characters in an internal path that are
not valid in a URL path MUST be percent-encoded as UTF-8. Consumers MUST
decode percent escapes before resolving the path within the bundle. A
fragment-only link refers to the current document; its fragment target is
not validated.

```markdown
See the [customers table](/tables/customers.md) for the join key.
```

A link from document A to document B asserts a *relationship*. The
specific kind (parent/child, references, joins-with, depends-on) is
conveyed by the surrounding prose, not by the link itself.

## 6. Conformance

A bundle is **conformant** with a declared BKF version when all applicable
requirements for that version are met:

- The selected bundle root contains a root `MAP.md` with the required
  `bkf_version` frontmatter.
- Every Markdown file other than root `readme.md` and the files of nested
  bundles (§3.3) is a bundle member.
  `MAP.md` files follow the structural map rules. Tracked members select a
  known profile and satisfy that profile's rules. Untracked members are
  unchecked by BKF. Reserved files are tracked as §3 says and appear only
  at the locations it gives.
- The `document` profile filename rule and reserved-file conventions are
  followed.
- Maps have valid structure, sections, markers, and inventories. Each
  inventory covers its exact scope, contains every in-scope tracked BKF
  document and child map once, uses the required file links and
  descriptions, and follows the required ordering.
- Required links use valid syntax and path forms. Internal file links
  resolve to existing files. External URLs are valid absolute URLs.
- Cross-profile YAML requirements and profile-specific fields have valid
  values and types. The `document` profile's fields are defined in the
  [frontmatter profiles](/format/frontmatter-profiles.md).

The root map declares the format version. An unrecognized declared version does
not establish conformance to that version. Consumers SHOULD still attempt
best-effort consumption. A validator reports that it cannot fully assess
conformance when it does not support the declared version.
