## Use

- Briefs are written and handoffs checked by the rules of the `delegate-work` skill.
- For a whole plan, use [Plan runs](#plan-runs).

## Phase runs

For a phase where agents work in parallel and each is reviewed by another agent (research collection, digest, and similar), use [scripts/phase-codex.sh](scripts/phase-codex.sh): no git, no branches, no diff. One agent is a phase with one pair.

- `phase-codex.sh start [-m model] [-e effort] [-f file] <run> <name> <agent-brief> <review-brief> [<name> <agent-brief> <review-brief>]...` creates one plain folder per agent under `~/.phase-runs/<run>/` (or `$PHASE_RUNS_DIR`), runs every agent in parallel, then its reviewer, and repeats by verdict until `pass`, `escalate` or a failure. Each agent writes one file, `output.md` unless `-f` names another. Run it with `run_in_background: true`; it prints each agent's final status. Defaults: `gpt-6-luna`, `xhigh`.
- The coordinator writes both briefs first. The script only appends the output file name, the reviewer's input and the verdict line format; everything about the phase belongs in the briefs.
- The reviewer ends `problems.md` with exactly one of `VERDICT: pass`, `VERDICT: back`, `VERDICT: escalate`; any other last line counts as a failed review. The script appends this format to every review prompt, so the role guides do not repeat it. `back` hands the list to the agent with its brief; `escalate` stops that agent and returns it to you; there is no round limit unless `PHASE_MAX_ROUNDS` is set (off by default; `research-run.sh` sets it to its own cap).
- Read the result in `<run>/log.tsv` and `<run>/<name>/rounds/<n>/problems.md` and `verdict`. A failed agent is logged in `status` and `log.tsv` and does not stop the others.
- `phase-codex.sh join <run>` concatenates the reviewed files under a heading per agent name, without reading them, and prints the path; it refuses while any agent is not `passed`. `phase-codex.sh clean <run>` deletes the run folder.
- Codex needs `--skip-git-repo-check` outside a repo, which the script passes. The sandbox confines writes to the agent's folder only outside `/tmp`, so run folders must not be under `/tmp`. HTTPS requests work in the sandbox; connections to a database do not (the host name does not resolve).

## Research runs

For a whole [research](../../library/workflow-types/research/research.md), use [scripts/research-run.sh](scripts/research-run.sh), which builds the briefs from fixed templates and chains the phases that need no one on top of `phase-codex.sh`.

- You write `objective.md`, `sourcemap.md` (one numbered niche per line) and `collectors.txt` (`name: 1,2,5` per line, the niches each collector covers), then run `research-run.sh start [-m model] [-e effort] <name> <objective.md> <sourcemap.md> <collectors.txt>` with `run_in_background: true`. It completes the source map with a cheap agent (its niches are shared out round-robin), collects with one agent per collector, joins, digests, and reviews each step. State is in `~/.research-runs/<name>/`, one numbered folder per phase.
- It stops at an `escalate` or a failure and writes `status.log` with where and why. After you fix the cause, `resume <name>` skips the finished phases and reruns the stopped one from scratch, keeping the old attempt as `<phase>.attempt-<time>`. `status <name>` prints `status.log`.
- Progress lines on stderr are followed by the step board; `research-run.sh board <name>` prints it on demand, and [test-research-run-board.sh](scripts/test-research-run-board.sh) checks the board with a fake `codex`.
- A review is capped at `RESEARCH_MAX_ROUNDS` rounds (default 3) and must give at least `RESEARCH_MIN_CHECKED` lines (default 3) under `## What I checked`, or it is repeated and then fails. `RESEARCH_GUIDES` names the folder with the role guides.
- When it prints `READY`, write the delivery, then `deliver <name> <delivery.md>` runs the review of the delivery (exit 0 `pass`, 1 `back`, 2 `escalate`); correct the delivery and run it again for the next round.
- `finish <name>` writes `status.md`, a readable summary of the phases (model and effort, rounds, what went wrong), from the run's `status.log`, copies the run into `records/research/<name>/` of the repository you run it in (it keeps the record: inputs, outputs, briefs, prompts, problems, verdicts and logs; it leaves out the script's own state files, the Codex events, stderr and last-message files, and the reviewer snapshots), checks that the copy matches, then deletes the run. `finish --delivery-only <name>` keeps only `delivery.md`. Folders of failed or redone attempts (`<phase>.attempt-<time>`) are left out unless you pass `--keep-attempts`.

## Plan runs

For a whole [plan](../../library/workflow-types/plan/plan.md), use [scripts/plan-run.sh](scripts/plan-run.sh). Run it inside the repository the plan changes.

- You write `goal.md`, one brief per unit, and `plan.txt`: one step per line, holding the unit briefs' paths (relative to `plan.txt`). A line with one brief is a unit run in the user's checkout; several on a line are a parallel group, each in its own git worktree, whose diffs an integration agent then applies to the checkout and a reviewer checks together. Run `plan-run.sh start [-m model] [-e effort] [-r review-effort] [-p checkpoints] <name> <goal.md> <plan.txt>` with `run_in_background: true`. `-e` sets the implementers' reasoning effort and `-r` the reviewers' (and the final review's); without `-r` both use `-e`. `resume` takes the same options and keeps what the run already stored.
- `start` creates `~/.plan-runs/<name>/` and begins the run at once; it fails if that folder exists. Do not create the folder by hand. Keep a plan that is ready but not to be launched yet as `goal.md`, `plan.txt` and the briefs in a folder outside `~/.plan-runs` (for example `~/.plan-runs-pending/<name>/`), and run `start` from it. The script prefixes each unit name with its step number, so name the brief files without one.
- Step numbers are the lines of `plan.txt`, and the finished and paused markers (`.done-S<n>`, `.paused-S<n>`) use them. A unit may be added in `00-input/order` and `00-input/units/` only after every step already finished or in progress, so that no marker changes meaning.
- A unit's diff is taken against the checkout as the previous step left it (`state-after-S<n>` in the run folder), as a snapshot of the working files, untracked ones included and ignored ones left out. So a commit, a dependency install or another unit's changes made while a unit is stopped never land in its diff, and edits to files git did not track yet are visible to the reviewer. A run begun with an older script keeps its old bases until a step passes under the new one. That holds for a plain step. A parallel group's units are made in worktrees from the checkout as it was when the group started, and the group's integration takes its base when it starts and keeps it, so a commit or edit made in the checkout after that shows up in the integration's diff, and its reviewer may call those files out of scope. Do not edit the checkout during a step; [`rebase-integration`](#reading-and-changing-a-stopped-run) is the emergency exit.
- A unit brief may hold a **gate**: a fenced block tagged `gate`, one command per line. After each implementation round the script runs these commands itself, in the checkout and outside any agent, and calls the reviewer only when all pass. A failing command sends the work back to the implementer with its output and no review, so a reviewer can never pass a red gate; a unit passes when the gate is green and the reviewer passes. `PLAN_GATE_TIMEOUT` (default 900 seconds) limits each command and `PLAN_MAX_GATE_ROUNDS` (default 5) stops a unit whose gate keeps failing. A brief with no gate is reviewed as before, and `start` notes which units have none. `plan-run.sh gates <plan.txt|name>` prints the commands of every unit (exit 1 if one has none), so the coordinator reads what code will run before `start` and whenever a unit changes.
- **The bridge.** An implementer's Codex sandbox cannot reach a database: HTTPS requests work, but the database host does not resolve (every `pnpm db:test:*` it ran failed on DNS; measured with Codex 0.163.0 on 2026-10-21). While an implementer works, the script serves `.plan-porteiro/ponte <command...>` in its checkout: the agent writes a request, the script runs it outside the sandbox and returns the output and the exit code. Only two kinds of request run: a `pnpm` script whose name matches a pattern in the repository's `.plan-run.json` (read from the unit's base commit, so a unit cannot widen its own list; refused if that script's definition differs from the base; the repository owns the guarantee that each listed script is safe, for example that it only reaches a test database) and the unit's gate commands exactly as written. `.plan-run.json` looks like `{ "bridge": { "pnpmScripts": ["^db:test(:[a-z0-9-]+)*$"] } }`, each entry a regular expression matched against the whole script name; without the file at the base only gate commands run, and the file should be committed, so that changes to it are reviewed like code. Requests run without a shell, so an agent supplies arguments and never shell syntax; everything else is refused, and every request is logged in `<run>/porteiro.log`. The folder is kept out of diffs and removed afterwards. Reviewers run read-only and have no bridge: they receive the gate result. The commands it runs include code the agent wrote, with the user's privileges, which is also true of the gate. `PLAN_PORTEIRO_TIMEOUT` (default 900 seconds) limits each request.
- `plan-run.sh` runs Codex in the `fast` service tier (quicker output, more plan quota per token). `PLAN_CODEX_TIER=` (empty) keeps the account default; `PLAN_CODEX_TIER=<tier>` picks another.
- The run also records, for each implementation round, the minutes, the agent's steps, the files in the diff and the input tokens (`<run>/metrics.tsv`, and a table in `status.md` after `finish`), to calibrate how big a unit should be. First measurement (17 units of one plan, one repository, one model, 2026-10-20, so a starting point and not a law): rounds of 14 to 60 agent steps took 1 to 5 minutes and rounds of 100 or more steps took 12 to 16 minutes; the slowest carried about 156 thousand input tokens per step against 30 to 60 thousand usual; a unit that repeated a known pattern across nine files took 32 steps. Correct these numbers after a plan.
- Progress lines are followed by a board of every step and unit; `plan-run.sh board <name>` prints it on demand.
- [scripts/test-plan-run-gate.sh](scripts/test-plan-run-gate.sh) tests the gate, the bridge, the metrics, the briefs of the integration and the final review, the run lock, `rebase-integration`, `accept-integration`, the usage-limit notice and the disk check with a fake `codex`, including that breaking each guard makes a test fail. Every `plan-run.sh` call in it has a time limit (`PLAN_TEST_LIMIT`, default 120 seconds), so a broken guard fails a test instead of hanging the suite.
- Each unit is implemented, then reviewed by another agent (verdict `pass`, `back` or `escalate`, capped at `PLAN_MAX_ROUNDS` reviews, default 3; that count, and `PLAN_MAX_GATE_ROUNDS`'s, start again at every `resume`). The run stops at an escalation or a failure and writes `status.log`; after you fix the cause, `resume <name>` continues, and a brief can be corrected in `00-input/units/` first. A unit copies its brief when it starts and a passed unit does not start again, so the correction reaches the units still to run, and always the integration of a group and the final review, which read the current briefs; the copy in `<unit>/brief.md` stays as what the implementer received. Where the two differ, the integration brief and the final review show both and tell the reviewer to judge against the current one and to say when a unit met the copy but not the current brief; the integration also writes a note in `status.log`, a stronger one when the gate differs, because that unit passed against another gate and the integration runs the current one. State is in `~/.plan-runs/<name>/`.
- `-p each` or `-p 2,4` pauses after those steps (exit 3, `PAUSED` in `status.log`) for the user to read or to merge outside work before the next step; some environments show exit 3 as a failure, but it is a pause. `resume -p none` clears it.
- When it prints `READY`, the final review is in `report.md`. Progress lines go to stderr, for example `[plan] S1 unidade 01-unit · ronda 1 · implementação`. `finish <name>` copies the record to `records/plans/<name>/` in the repository; `finish --discard <name>` deletes the run.

### Who reads what

| Agent | Brief | `goal.md` |
|---|---|---|
| Implementer and reviewer of a unit | the unit's own copy, made when the unit starts | no |
| Integrator and reviewer of a group's integration | the current brief in `00-input/units/` of every unit | yes, read from `00-input/goal.md` when the integration starts; a `gate` block in it is not run |
| Final review | the current briefs | yes |

- A rule the unit reviewers must apply goes in the briefs of the units still to run: `goal.md` never reaches them.
- `goal.md` serves the integration and the final review to judge how the units fit and what is out of scope; it adds no criteria to the briefs. It may also hold a note on how the run was carried out, for example "the owner committed in the checkout during step 2: ignore those files".
- `resume` does not recreate worktrees. A group's worktrees are made once, from the checkout as it was when the group started, so a change to a shared file reaches a unit still to run only if it was in the checkout before the group started; otherwise put it in that unit's brief.

### Reading and changing a stopped run

- **Lock.** While a `plan-run.sh` works on a run it holds `<run>/.lock` (its pid). A second `resume`, a `finish`, `rebase-integration` and `accept-integration` refuse while a live `plan-run.sh` holds it; a lock whose pid is gone, or now belongs to another program, is stale and is replaced.
- **`plan-run.sh rebase-integration <name> <step> [--paths <path>...]`** moves the base of a group's integration when the checkout was edited after the integration started and those edits sit in its diff. It is an emergency exit: the rule is not to edit the checkout during a step.
  - Without `--paths`, the base becomes the checkout minus the diffs of the units already applied. It refuses once the integrator ran, in this attempt or an earlier one, because the integrator's own edits would then become base and hide from the reviewer; it also refuses, naming the git error, when the checkout changed a file of a unit's diff.
  - With `--paths`, the base stays and the given files or folders (relative to the repository) take the checkout's current version as their base. It refuses paths that hold a file of a unit's diff, and paths where nothing differs. It prints the files that leave the diff and writes the same list to `status.log`. If one of them is an edit of the integrator, the reviewer will not see it either, so name only what the owner touched.
  - Both keep the old base as `.base.before-rebase-<time>` in the integration folder. Then `resume`.
- **`plan-run.sh accept-integration <name> <step> --why <text>`** closes a group's integration by hand, when the owner judged the combined result. It applies and reviews nothing: it needs every unit of the step `passed` with its diff applied, marks the integration done, removes the worktrees and writes in `status.log` who closed it, at which `HEAD`, and why. Then `resume`.
- **Usage limit.** When Codex reports that the account is out of quota, the run stops with the reason `usage limit reached` and `status.log` gets `QUOTA: <the text after "try again at">`, kept as Codex wrote it and not parsed. `resume` after that time.
- **Disk.** Before a parallel group starts, the first worktree measures what one takes (`df` before and after); the others are projected from it with a margin of a quarter, and the step is refused, with the worktrees removed, if they will not fit. `status.log` records the measure. The estimate covers worktrees only, not what the units create while they run (temporary database clusters, build output), and `df` is not exact.

## Council runs

For a [council](../../library/workflow-types/council/council.md), use [scripts/council-run.sh](scripts/council-run.sh). `start [-m model] [-e effort] <name> <brief.md>` runs five advisors apart, anonymizes their responses into a packet with the key kept in `02-packet/key.md`, runs five reviewers apart and stops at `READY`. You then write the report and run `check <name> <report.md>` (exit 0 `pass`, 1 `back`, 2 `escalate`). `resume`, `status` and `finish` work as in plan runs; state is in `~/.council-runs/<name>/` and `finish` keeps the record in `records/councils/<name>/`. Progress lines on stderr are followed by a board of the steps; `council-run.sh board <name>` prints it on demand (covered by [scripts/test-council-run-board.sh](scripts/test-council-run-board.sh)).

## Review runs

For a [code review](../../library/workflow-types/code-review/code-review.md), use [scripts/review-run.sh](scripts/review-run.sh): `start [-m model] [-e effort] [-2] [-s spec.md] [-d standards.md]... [-g command]... <name> <target>`, where the target is `working-tree` or a revision range such as `main...feature`. Each `-g` is a command that verifies the change (tests, type check, lint): the script runs them itself in the repository before any agent starts, records command, output and exit code in `gate.md`, hands the file to every agent and shows it at the top of the report; a red command does not stop the review but stands in the report, and with no `-g` the report says the checks were not run. `REVIEW_GATE_TIMEOUT` (default 900 seconds) limits each command. [scripts/test-review-run-gate.sh](scripts/test-review-run-gate.sh) tests this with a fake `codex`. A Standards and a Spec agent review the pinned diff apart, a checker per axis confirms each finding, and the script writes `report.md`; `-2` adds a second reviewer per axis. State is in `~/.review-runs/<name>/`, and `finish` keeps the record in `records/reviews/<name>/`.
- Progress lines on stderr are followed by the step board; `review-run.sh board <name>` prints it on demand, and [test-review-run-board.sh](scripts/test-review-run-board.sh) checks the board with a fake `codex`.

## Shared code

[scripts/lib-codex.sh](scripts/lib-codex.sh) holds what `phase-codex.sh` and the four run scripts share: running a Codex agent, running a set of agents in parallel, reading a verdict and checking the "What I checked" section. Source it; it defines functions only.

[scripts/lib-inject.sh](scripts/lib-inject.sh), which `lib-codex.sh` sources, adds text to a brief just before `codex_run` starts the agent, so that a rule is written once and every brief that needs it carries it. A role guide asks for a file with a line of its own, `<!-- inject: ../../modules/determinism.md -->` (a Markdown file, path relative to the guide); the script finds the guides a brief names (`role guide: <absolute path>.md`), appends the body of each requested file once, under a heading that says where it came from, and records that in the brief, so the brief kept in the run is what the agent read. A missing file stops the agent from starting. Any guide can ask for any Markdown file; no script changes. [scripts/test-inject.sh](scripts/test-inject.sh) tests it with a fake `codex`, and checks that every directive in the real guides resolves.

## Safety and gotchas

- Runs use the `workspace-write` sandbox. It confines writes to the agent's folder, but an agent can still read files outside the checkout, such as the login sessions of CLI tools in the home folder, and reach HTTPS, so it can use any session left open. The repository's own rules say what to keep logged out.
