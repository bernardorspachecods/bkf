# Running a plan

The script is [scripts/plan-run.sh](scripts/plan-run.sh); run it inside the repository the plan changes. The commands every run script shares (`resume`, `status`, `board`, `finish`, state, backend, quota, lock) are in the Run commands section of [SKILL.md](SKILL.md#run-commands).

`plan-run.sh start [-m model] [-e effort] [-r review-effort] [--review-model model] [--review-backend backend] [--takeover-after N] [--takeover-review MODE] [-p checkpoints] [--in-place] [--from <ref>] <name> [<goal.md> <plan.txt>]`: without the two paths it starts the pending plan called `<name>` of this repository (see below); `-e` sets the implementers' reasoning effort and `-r` the reviewers' (and the final review's); without `-r` both use `-e`. `--review-model` runs every reviewer (and the final review) on another model than the implementers, and `--review-backend` (`codex` or `claude`) on another backend; a reviewer backend needs its own `--review-model`, since `-m` belongs to the implementers' backend. Without them the reviewers use `-m` and the run's backend. `--takeover-after N` is how many reviews may send a unit back before the coordinator takes it over (default `2`, `0` turns it off; see Takeover below), and `--takeover-review MODE` is what checks the coordinator's fix, `reviewer` or `none` (default `reviewer`). `resume` takes the same options and keeps what the run already stored.

- You write `goal.md`, one brief per unit, and `plan.txt`: one step per line, holding the unit briefs' paths (relative to `plan.txt`). A line with one brief runs a unit in the run's worktree (see below); several briefs on a line run as a parallel group in separate worktrees, followed by integration and review of the combined result. Before creating a group the runner checks the disk and refuses the step if the worktrees will not fit (the first worktree is measured and the others projected from it with a quarter of margin; the estimate does not cover what units create while they run).
- **Pending plans.** Keep a plan that is ready but not to be launched yet in `~/.plan-runs-pending/<repo>/<name>/` (`<repo>` is the folder name of the checkout the script runs in, `Path(repo).name`): `goal.md`, `plan.txt` and the briefs. In a linked git worktree, this is the worktree folder name, not the main repository's folder name; put pending plans there and find runs under that same name. `plan-run.sh pending` lists plans for the checkout you are in, and `plan-run.sh start <name>` starts one and moves its folder into the run, to `00-input/source/`, so a single copy stays the current one. The script prefixes each unit name with its step number, so name the brief files without one. `PLAN_PENDING_DIR` or `HARNESS_PENDING_DIR` sets another root.
<a id="the-runs-worktree"></a>

- **The run's worktree.** By default a run works in a git worktree of its own, `<run>/tree`, on the new branch `plan/<name>` cut from `HEAD`, and the repository's checkout is not touched. `start` refuses when the checkout has uncommitted changes, because a worktree cut from `HEAD` would not hold them: commit or stash them, start with `--from <ref>` to cut the worktree from that commit and ignore them (the way to start while other sessions leave files uncommitted), or start with `--in-place` (or set `PLAN_IN_PLACE=1`) to work in the checkout as before. The runs folder and the record kept by `finish` belong to the repository's main checkout, also when the command runs inside one of its worktrees. After each unit passes, and after each group's integration, the script commits what changed on the branch (`plan <name>: <unit>`), so every unit is one commit; a failed commit is only noted in `status.log`. When the run is finished, `finish` removes the worktree and keeps the branch: review it and merge it. `finish --discard` deletes both. A worktree holds only the files git tracks, so the repository's committed `.plan-run.json` can say what to set up in it, before the first unit and outside any agent: `{"worktree": {"copy": [".env.test"], "prepare": ["pnpm install --frozen-lockfile"]}}`. `copy` lists files or folders, relative to the repository, taken from the checkout when they exist (never a secret the agents should not read: they can read everything in the worktree); `prepare` lists commands run in the new worktree, a failing one stops the start and removes the worktree. `PLAN_PREPARE_TIMEOUT` (default 1800 seconds) limits them; the output is in `<run>/prepare/`.
- Step numbers are the lines of `plan.txt`; the markers `.done-S<n>` and `.paused-S<n>` use them. A unit may be added in `00-input/order` and `00-input/units/` only after every step already finished or in progress, so that no marker changes meaning.
- **Diff base.** A unit's diff is taken against the checkout as the previous step left it (`state-after-S<n>` in the run folder): a snapshot of the working files, untracked ones included and ignored ones left out. A commit, a dependency install or another unit's changes made while a unit is stopped never land in its diff.

Parallel groups, integration and recovery of a stopped run: [run-recovery.md](run-recovery.md#diff-base-for-parallel-groups).

In the default mode the checkout is yours and the units never see what you do in it. With `--in-place` do not edit the checkout during a step; `rebase-integration` is the emergency exit.
<a id="gate"></a>
- **Gate.** The gate's format and what it must contain are in [SKILL.md](SKILL.md#2-the-unit-brief). After each implementation round the script runs the commands itself, in the checkout and outside any agent, through `bash -c` (a shell), and calls the reviewer only when all pass. A failing command sends the work back to the implementer with its output tail and no review, so a reviewer can never pass a red gate. A unit passes only when its gate is green and the reviewer passes. `PLAN_GATE_TIMEOUT` (default 900 seconds) limits each command (a timeout stops its process group, exit code 124); `PLAN_MAX_GATE_ROUNDS` (default 5) stops a unit whose gate keeps failing. This gate-failure cap is larger than the review cap; when it is reached, the unit stops for the coordinator. `start` notes the units with no gate, and `plan-run.sh gates <plan.txt|run-name|pending-name>` prints the commands of every unit (exit 1 if one has none). It accepts a plan path or an existing run name; pending-plan names are not resolved yet. The coordinator's requirement to read the gates is in [SKILL.md](SKILL.md#1-the-goal-and-the-units).
- **Regression check.** A unit's gate sees only its own unit, so a break that unit made elsewhere (an existing test gone red) shows up units later, in an unrelated brief. A file `regression.gate` next to `plan.txt` (one command per line, blank lines and `#` comments skipped; copied into the run at `start`, so editing it later changes nothing) holds the commands that decide the whole plan, such as the full database suite. The script runs them in the run's checkout, outside any agent, after each step you chose to pause at with `-p` (before the pause) and once before the final review; without `-p` it runs only that last time. `PLAN_GATE_TIMEOUT` limits each command. A failing command stops the run with `STOPPED at the regression check after S<n>` and the output in `<run>/regression-S<n>/` (`regression-final/` for the last): repair it, then `resume`, which repeats only the check (and then the pause) without running the step again. The check does not send the work back to an implementer, and in a step with parallel units it cannot say which unit broke it.
- **Shared memory.** On macOS, before each unit's first round the script counts the free System V shared-memory segments (`ipcs -m -a` against `kern.sysv.shmmni`, 32 by default). With fewer than `HARNESS_SHM_MIN_FREE` free (default 4, `0` turns the check off; other systems are not checked) the unit does not start: it stops with `not started, only N of 32 ... segments are free`, which says that `initdb` would fail with `No space left on device` (not the disk), names the segments no process is attached to and prints the `ipcrm -m <id> ...` line to run if none of your databases is running. The script never removes segments itself. The cause is usually test databases killed before their teardown; making the repository's database test teardown remove its cluster and segment is the lasting fix and belongs to that repository.
- **Conversations.** An implementer, a reviewer and an integrator keep their own conversation across rounds and across `resume`: the script saves the session id of each in `<unit>/session-implement.json`, `<unit>/session-review.json` and `<unit>/session-integrate.json` (a group's integration has its own folder), and the next round or the resumed run continues that session with a short message instead of starting a new agent with the brief and the handoff pasted in. The message holds only what is new: the problems of the gate or the review, the last problems found before a stop (after `escalate`, `BLOCKED`, `STALLED`, an error), the current brief when it was corrected, and what you said with `plan-run.sh resume --say "<text>" <name>` (or `--say-file <file>`). `--say` reaches the agents the resume continues, the way a message in a conversation would: use it to answer a `BLOCKED` or to explain what you changed in the checkout. A reviewer continues its own conversation, never the implementer's, so it stays independent of the implementer's reasoning. Codex sessions resume with `codex exec resume <id>` (the sandbox goes in as `-c sandbox_mode=...`, which `exec resume` needs because it takes no `-s`), Claude sessions with `--resume <id>`. A session that cannot be resumed (deleted, or for another backend or folder) is noted in `status.log` and the agent starts a new conversation with the full prompt, as before. Edits you made to the checkout between the stop and the resume are told to the agent as possible, not listed: say what you changed with `--say`.
- **Premises.** A fence tagged `premise` in a brief lists commands that prove the facts the unit relies on (one per line, as in a gate). The script runs them before the unit's first round, in the unit's checkout, outside any agent, with the gate's timeout; one failing stops the unit with `the premise ... is false at this unit's start`, status `blocked`, no implementer launched and the output in `<unit>/premise/`. A resumed unit runs them again, so correcting the brief or the checkout is checked before the implementer is paid for. When a unit is retried (`resume` on a unit that already ran), the first round's prompt carries the earlier attempt's handoff, so a new implementer starts from what the old one found. The agent's conversation is resumed too (see Conversations below).
- **Repeated failures.** A failed gate command gets one immediate repeat; if it passes then, the round is treated as flaky. The run stops early when the same gate fails the same way in consecutive rounds or the reviewer sends the unit back twice for the same files.
<a id="brief-problems"></a>
- **Brief problems.** An implementer may end with `BLOCKED: ...` when the brief prevents progress, and a reviewer may return `VERDICT: brief` when the brief is contradictory or impossible; either stops the unit and signals the coordinator that the brief may be wrong.
<a id="brief-lint"></a>
- **Brief lint.** `plan-run.sh gates <plan.txt|run-name|pending-name>` prints brief lint after the gate commands: errors make the command exit 1, while warnings do not. It keeps the set of paths that the `Removes` and `Creates` sections of the earlier steps leave, plus the brief's own, and checks each gate command against that end state: a command that uses a removed path is an error, and a script that is missing now but created earlier is not warned about. Units on the same line do not see each other's sections. It reads only declared paths, so an omitted `Removes` goes unseen. `start` runs the same lint and refuses to create the run while it reports an error. `resume` lints the current briefs in `00-input/units/` the same way, so a corrected brief cannot bring an error back; units that already passed are not reported. `PLAN_ALLOW_LINT_ERRORS=1` goes ahead anyway, for a lint that is wrong.
<a id="rehearsal"></a>
- **Rehearsal.** `plan-run.sh rehearse <plan.txt|run-name|pending-name>` runs the plan's gate commands informationally before `start`; failures are reported but do not fail the rehearsal. Identical commands (such as a shared repository-wide check) run once and the result is reported for every unit that lists them. It accepts a plan path, the name of an existing run or the name of a pending plan of this repository. This catches commands that cannot run as written, such as `bkf validate` without its required argument. The coordinator's rehearsal requirement is in [SKILL.md](SKILL.md#1-the-goal-and-the-units).
<a id="the-bridge"></a>

- **The bridge.** While an implementer works, `.plan-porteiro/ponte <command...>` lets it request an allowed command outside the Codex sandbox and returns the output and exit code. The committed `.plan-run.json` at the unit's base lists allowed `pnpm` script-name patterns under `bridge.pnpmScripts` (for example `{ "bridge": { "pnpmScripts": ["^db:test(:[a-z0-9-]+)*$"] } }`; the script definition must match the base version); the bridge also accepts the unit's gate commands exactly as written. It runs an exact gate command through `bash -c` (a shell), and runs an allowed `pnpm` script directly as argv without a shell. Requests and refusals are logged in `<run>/porteiro.log`; `PLAN_PORTEIRO_TIMEOUT` (default 900 seconds) limits each. Reviewers are read-only and do not use it.
  - A measurement that takes more than about 30 minutes does not go through the bridge: a request is cut at `PLAN_PORTEIRO_TIMEOUT`, and an implementer waits only a few minutes for a command. Let the unit's gate run it (`PLAN_GATE_TIMEOUT`), or run it yourself and put the result in the brief as a fact. Both timeouts are environment variables of the process, so set them on every `start` and `resume`. A background process started inside the Codex sandbox (`nohup … &`) may fail (`zsh: nice(5) failed`) or never reach the bridge: do not rely on it.
  - The bridge reads `.plan-run.json` from the unit's base (`state-after-S<n>`), not from `HEAD`: correcting the file in the repository is not enough. Change the allowed list with the run stopped, and say in the final review that the list grew, because it widens what agents may run.
- Each unit is implemented, then reviewed by another agent (verdict `pass`, `back` or `escalate`, capped at `PLAN_MAX_ROUNDS` reviews; with takeover on, a unit that keeps coming back reaches the coordinator first, see Takeover). A brief can be corrected in `00-input/units/` before `resume`: a unit copies its brief when it starts and a passed unit does not start again, so the correction reaches the units still to run and always the integration of a group and the final review, which read the current briefs; the copy in `<unit>/brief.md` stays as what the implementer received. Where the two differ, the integration and the final review show both and judge against the current one, and the integration notes in `status.log` that a unit passed against another gate.
- `-p each` or `-p 2,4` pauses after those steps (exit 3, `PAUSED` in `status.log`) for the user to read or to merge outside work; some environments show exit 3 as a failure, but it is a pause. `resume -p none` clears it.
- `plan-run.sh` runs Codex in the `fast` service tier. `PLAN_CODEX_TIER=` (empty) keeps the account default; `PLAN_CODEX_TIER=<tier>` picks another.
- The run records for each implementation round the minutes, the agent's steps, the files in the diff and the input tokens (`<run>/metrics.tsv`, and a table in `status.md` after `finish`), to calibrate how big a unit should be. First measurement (17 units of one plan, one repository, one model, 2026-10-20, so a starting point and not a law): rounds of 14 to 60 agent steps took 1 to 5 minutes and rounds of 100 or more steps took 12 to 16 minutes; the slowest carried about 156 thousand input tokens per step against 30 to 60 thousand usual; a unit that repeated a known pattern across nine files took 32 steps. Correct these numbers after a plan.

Parallel groups, integration and recovery of a stopped run: [run-recovery.md](run-recovery.md#who-reads-what).

## Takeover

A weaker implementer often fails the same small point round after round. With `--takeover-after N` (default 2), the N-th review that sends a unit back does not return it to the implementer: the run stops with the unit `takeover` and the coordinator applies what the reviewer listed.

```
implement ─► gate ─► review ─ back ─ (N reviews) ─► status takeover, the run stops
                                                      coordinator edits the checkout
                                                      ▼
                                     plan-run.sh close <name>
                              gate ─► the same reviewer, on the delta ─ pass ─► unit done, the run continues
                                                                       back ─► takeover again
```

- **What the coordinator gets.** The stop message names the unit, the last review's `problems.md`, the checkout (the unit's worktree in a group; the run's checkout for an integration) and the brief. Apply every problem listed, whatever its size. The implementer's handoff is not evidence; do not rely on it.
- **`close <name>`** closes every unit or integration in takeover, then resumes the run. It runs the unit's gate (a gate that fails keeps the unit in takeover and starts no reviewer), refuses a close with no change since the takeover, and with `--takeover-review reviewer` resumes the unit's reviewer conversation with the delta since the takeover (`close/<k>/delta.patch`) and its own earlier problems. With `--takeover-review none` only the gate checks the fix and the unit is marked `reviewed: no` in `closed-by-coordinator`; say so in the final report, because no independent review saw that fix.
- **What does not become a takeover.** `escalate`, `brief`, a blocked implementer and a gate that fails the same way twice still stop the run as before: they point to the design or the brief, not to a small defect. `--takeover-after 0` keeps the old behaviour (a round cap, `PLAN_MAX_ROUNDS`).
- **Groups.** Each unit of a parallel group takes over on its own; the others finish. `close` closes only the units in takeover, and the units that passed are not run again. The integration of the group takes over by the same rule.
- **Cost.** The coordinator's own context grows with every fix: `--takeover-after 1` is the fastest plan and the most expensive for the coordinator.
- A plain `resume` of a unit in takeover forgets the takeover and runs the implementer again, as before.
