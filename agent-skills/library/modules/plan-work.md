# Plan work

- A plan states the intended outcome, the boundaries, the work needed, and how completion will be recognized, in terms someone else can check and written before the work starts, so reviewers can test against them without relying on the producer's account. Keep it as short as the work allows; add units, research or review only for a concrete need, and do not create a parallel tracker when a canonical plan already owns the work.
- Do not choose the plan's format for the user: ask whether they want a conversation plan or a plan that runs on a script with units, explaining the difference neutrally. A conversation plan stays in the conversation. A plan that runs follows the plan workflow guide. The coordinator decides the order of the units and which run in parallel, and tells the user. It suggests where to pause, with the effect of each pause, and the user decides the pauses and the model. Ask before adding a local exception.
- Present the finished plan and wait for the user's agreement on scope, outputs, sequence and settings before any assigned work starts. That agreement authorizes in-scope assignments but does not waive a checkpoint the user asked for. If a request conflicts with the plan's settings, stop and reconcile the plan first.
- Agreed requirements are mandatory. Resolve minor issues within the approved scope; a requirement that cannot be met within it, or a decision that changes it, is handled as [act-within-scope](/modules/act-within-scope.md) says.
- How to split work into units, and how big a unit may be, is owned by the [plan workflow guide](/workflow-types/plan/plan.md). When suggesting the plan's settings, show the split with the reason for each cut.
