# Plan work

- A plan states the intended outcome, the boundaries, the work needed, and how completion will be recognized, in terms someone else can check and written before the work starts, so reviewers can test against them without relying on the producer's account. Keep it as short as the work allows; add units, research or review only for a concrete need, and do not create a parallel tracker when a canonical plan already owns the work.
- Do not choose the plan's format for the user: ask whether they want a conversation plan or a plan that runs on a script with units, explaining the difference neutrally. A conversation plan stays in the conversation. A plan that runs follows the plan workflow guide. Likewise recommend the settings (how many units, which run in parallel, where to pause) with their effect, let the user choose, and ask before adding a local exception.
- Present the finished plan and wait for the user's agreement on scope, outputs, sequence and settings before any assigned work starts. That agreement authorizes in-scope assignments but does not waive a checkpoint the user asked for. Pause earlier for a blocker, an unmet requirement, or a decision that changes the approved scope, and if a request conflicts with the plan's settings, stop and reconcile the plan first.
- Agreed requirements are mandatory. Resolve minor issues within the approved scope. If a requirement cannot be met within scope, stop and name the requirement and the blocker.
- Split work into a separate unit only when it has review criteria of its own that a reviewer can judge apart from neighboring work, when a dependency or worthwhile parallelism separates it, when the user wants a checkpoint there, or when merging it would overload one brief. Otherwise fold it into the unit that consumes it; each unit costs a full review round, so size units by their work and risk. When recommending settings, show the split with the reason for each cut.
