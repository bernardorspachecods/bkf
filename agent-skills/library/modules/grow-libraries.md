# Grow the libraries

- A repository's own procedures live in `repo-library/` at the repository root, which is a BKF bundle in the same shape as this library: modules for rules in `modules/`, workflows for staged procedures in `workflow-types/`, and a `MAP.md` with the generated member inventory. An entry's frontmatter `description` states what it is or covers, in one sentence with no "open when" or "use when" phrase. If the folder does not exist yet, create it with the root `MAP.md`.
- A candidate is a procedure or rule set the work has applied more than once, or one the user says always applies here, and that is scoped to an activity (for example, editing the database). Prose about how the repository works, with no activity to act on, is not a candidate. A third trigger is an external source (a page, document, or file) the user wants turned into a rule. It is a candidate only when it holds a rule or procedure scoped to an activity; if it holds only information, say so and stop.
- Propose a candidate; do not write it first. Name the activity, the rules or stages it would hold, and whether it is a module or a workflow; also name the two or three closest existing entries and what each owns, so the user can inspect and correct the overlap check. Then wait for the user's answer.
- Decide the destination when proposing. A rule that depends on this repository's code, structure, or conventions goes to `repo-library/`. A rule that would hold in any repository goes to the general library instead; this is rarer, and the proposal says why. Write nothing in the general library without the user's answer. An entry derived from a source names it (URL or path, and the date collected), and each of its claims is located in the source exactly as written, as the research collection guide requires.
- Write a module for one rule set about one activity. Write a workflow only when the procedure has stages, such as a release or a migration.
- Before writing, check the map for an entry with the same activity and extend it when it fits. Have a fresh agent who did not draft the proposal independently find where the proposed rule already lives, in the repo-library and the general library; give it only that job, have it report only the overlap locations, and have it make no edits. Use the review rules in [review-work](/modules/review-work.md). Do not duplicate a rule the general library already owns; the repo entry holds only what is specific to the repository.
- After writing, run `bkf inventory --write` and `bkf validate` on `repo-library/`, and say what was added. If the `bkf` command is not installed, do not write the map by hand: tell the user the tool is missing.
